# 业务速览与操作手册

适用对象：第一次接触项目、希望先理解业务再看代码的人。示例设备来自初始化数据；完整版运行与实际评测记录见 [验证记录](VERIFICATION.md)。代码学习从 [12 项能力路线](LEARNING_PATH.md) 开始。

## 1. 用一句话理解项目

这是一个扫地机器人智能售后助手：用户通过聊天查产品手册、查自己的设备状态和耗材寿命，故障无法解决时，确认创建售后工单，再查询未关闭工单。

典型场景：用户的 CleanBot X1 出现 E03 → 询问故障含义与处理办法 → 查询设备状态和主刷寿命 → 如果问题反复，申请报修 → 核对并确认 → 获得工单编号。

业务目标是帮助用户自助排障，并把需要人工处理的问题记录为工单。当前实现到“创建和查询工单”为止，没有维修人员派单、上门预约、维修进度更新、结单、退款或支付流程。回答中建议“转人工”也不代表系统已接通人工客服。

## 2. 先认识角色和数据

| 概念 | 业务含义 | 本项目示例 |
| --- | --- | --- |
| 租户 | 相互隔离的企业或客户组织 | tenant-a、tenant-b |
| 用户 | 拥有设备、发起咨询和报修的人 | user-001 |
| 设备 | 用户的扫地机器人，带有状态、电量、主刷寿命等信息 | device-001 |
| 知识库 | 产品手册、故障处理、维护和隐私说明 | E03 故障处理、耗材维护指南 |
| 工单 | 记录设备故障的售后请求 | 新建状态为 OPEN（未关闭） |
| 管理员 | 通过管理接口维护知识库、运行评测 | 请求示例中的 admin-001 |

页面默认身份是 tenant-a / user-001，项目访问密钥是 demo-key（如果后端修改过，以实际配置为准）。当前身份设置是演示机制，没有完整的注册登录与账号管理页面。

初始化设备如下；已有数据库中的实际数据可能不同。设备数据是数据库中的演示记录，当前没有真实硬件遥测接入。

| 设备 | 归属 | 型号 | 状态 | 电量 | 主刷剩余寿命 | 故障码 |
| --- | --- | --- | --- | --- | --- | --- |
| device-001 | tenant-a / user-001 | CleanBot X1 | OFFLINE（离线） | 18% | 12% | E03 |
| device-002 | tenant-a / user-001 | CleanBot X2 | CHARGING（充电中） | 76% | 68% | 无 |
| device-900 | tenant-b / user-900 | CleanBot Pro | CLEANING（清扫中） | 54% | 80% | 无 |

## 3. 打开系统

已经启动后端时，直接打开 <http://localhost:8080/>。

使用现有本机 VMware 环境：先启动虚拟机，重新加载 Maven，再在 IDEA 选择 **SupportAgent - VMware** 运行；详细步骤见 [本机 IDEA + VMware 数据库](LOCAL_VM.md)。也可以在项目根目录 PowerShell 执行 `./scripts/start-local.ps1`，两种方式选一种。

如果希望使用不依赖虚拟机和模型密钥的默认模式，在已安装 Java 17 和 Maven 的环境下，不启用额外 Profile，执行：

```powershell
mvn -s maven-settings.xml spring-boot:run
```

默认模式使用 H2 内存数据库，后端重启后演示期间创建的工单不会保留。启用 postgres 后业务数据存入 PostgreSQL。是否调用真实模型由 ai Profile 决定，页面外观无法证明已启用模型。

页面右上角显示“服务已连接”表示健康检查通过，不代表真实模型调用已经验证成功。

## 4. 十分钟走完业务流程

建议按下面顺序点击左侧场景按钮，或复制问题到输入框。默认演示模式通过关键词选择业务功能，每次问一个明确问题并带设备编号最容易观察结果。

| 步骤 | 页面操作 / 输入问题 | 应观察到的结果 |
| --- | --- | --- |
| 1. 故障排查 | 点击“故障排查”：`E03 是什么，应该怎样处理？` | 根据手册解释主刷缠绕，给出关机清理等步骤；回答下方可展开“参考来源” |
| 2. 查设备 | 点击“设备状态”：`查询 device-001 当前状态和电量` | 初始化数据为离线、电量 18%、故障码 E03 |
| 3. 查耗材 | 点击“耗材建议”：`查询 device-001 的耗材和主刷寿命` | 主刷寿命 12%，建议准备更换 |
| 4. 查已有工单 | 点击“我的工单”：`查询 device-001 的未关闭工单` | 返回已有 OPEN 工单；全新数据库通常为 0 条 |
| 5. 申请报修 | 点击“申请报修”：`给 device-001 创建工单，E03 反复出现` | 提示需要明确确认，此时尚未创建工单 |
| 6. 确认提交 | 点击回复下的“核对并确认创建工单”，核对弹窗内容，再点击“确认并提交” | 返回工单编号、设备、故障描述、OPEN 状态及创建时间 |
| 7. 验证结果 | 再点击“我的工单” | 能查到刚创建的工单 |

弹窗选择“暂不提交”不会提交该次报修。在输入框只输入“确认”不能替代页面确认按钮：后端需要当前请求携带确认标记及幂等键。

创建工单会写入当前数据库，但本项目没有对接外部维修服务；生成编号不意味着已经安排维修。

## 5. 再做三个对照，理解业务规则

### 对照一：换一台自己的设备

分别发送 `查询 device-002 当前状态和电量` 和 `查询 device-002 的耗材和主刷寿命`。初始化数据为充电中、电量 76%、主刷寿命 68%，应提示暂不需要更换主刷。

主刷建议的实际代码规则：剩余寿命小于 10% 时尽快更换；大于等于 10% 且小于 20% 时准备更换；大于等于 20% 时暂不需要更换。耗材查询工具当前只读取主刷寿命；滤网、边刷的维护方法属于知识问答。

### 对照二：查询其他租户设备

保持默认身份，发送 `查询 device-900 当前状态和电量`。应拒绝访问或说明设备不存在 / 不属于当前用户，不应返回该设备详情。知识检索也按租户隔离。

### 对照三：区分故障知识和设备事实

`E03 是什么，应该怎样处理？` 查询的是产品知识；`查询 device-001 当前状态和电量` 查询的是这台设备的数据库记录。阅读故障处理建议不会自动修复设备，也不会把数据库中的 E03 清掉。

## 6. 页面日常操作与常见问题

| 情况 | 操作与说明 |
| --- | --- |
| 发送和换行 | Enter 发送，Shift + Enter 换行 |
| 切换身份 / 访问密钥 | 左下角“连接设置”填写访问密钥，服务端验证后显示其绑定身份，并开启新对话；身份字段只读，不是 DeepSeek 密钥 |
| 开启新对话 | 清空页面聊天记录并生成新会话 ID；不会删除数据库中的工单 |
| 刷新页面 | 页面聊天记录清空、会话 ID 更新，连接设置恢复默认值 |
| 想核对回答依据 | 展开“参考来源”；当前显示来源名称和路径，不是可直接打开的手册文件链接 |
| 回复出现字段名或数据结构 | 默认演示应答器会直接展示工具结果，如 batteryLevel 是电量，brushLifePercent 是主刷剩余寿命 |
| 访问验证失败 | 检查项目 API Key 是否正确；租户、用户和角色由服务端绑定，不能通过改请求头取得他人权限 |
| 设备查询失败 | 检查编号和设备归属；不存在或无权限的设备统一提示核对编号，不应再直接报 HTTP 500 |
| 工单提交超时 | 先查询未关闭工单；需要重试时使用原消息的“重试这条请求”，再次核对确认，原请求会复用同一幂等键 |
| 又发送了一次相同报修内容 | 新消息会生成新幂等键，可能创建另一张工单；相同文字不等于同一次请求 |
| 服务连接异常 / HTTP 错误 | 确认后端运行；VMware 模式检查虚拟机和数据库服务；将回答中的 TRACE 编号（如有）与错误现象交给开发者排查 |
| HTTP 429 / 请求过于频繁 | 当前用户、租户或服务额度已满，请稍后重试；换会话不能绕过用户限额 |
| HTTP 503 / 服务暂时不可用 | 并发保护或依赖暂时不可用；涉及报修先核实已有工单，不要反复换请求编号提交 |
| 回答不理解复杂追问 | 未启用 ai 时使用关键词规则，虽然有会话存储，但演示应答器不利用历史理解追问；先使用本文完整示例问题 |

## 7. 管理员能做什么

目前没有可视化管理后台。使用项目根目录 [requests.http](../requests.http) 中的接口示例操作：

| 能力 | 接口 | 说明 |
| --- | --- | --- |
| 新增 / 更新知识 | POST /api/admin/knowledge | 提供 documentId、title、source、content；相同租户和 documentId 用于更新 |
| 删除知识 | DELETE /api/admin/knowledge/{documentId} | 删除指定租户中的文档 |
| 检索评测 | POST /api/admin/evaluations/run?mode=retrieval&limit=50 | 运行预置用例，帮助检查检索效果 |
| 回答评测 | POST /api/admin/evaluations/run?mode=agent&limit=50 | 运行预置回答评测 |

管理请求必须用管理员 API Key（本机生成于 `.env.local` 的 `SUPPORT_ADMIN_API_KEY`）。普通密钥附加 `X-Role: ADMIN` 会被拒绝。管理员身份用于维护本租户知识，并不等于拥有 user-001 的设备。修改知识后，用普通用户密钥从聊天页面核对回答及来源。

正式模式使用独立 `.env.production.local` 凭据，`demo-key` 不可用，在线评测默认关闭；详情见 [多人并发与正式运行](CONCURRENCY.md)。每位真实用户需要独立身份，不能共用同一个访问密钥。

新增 `POST /api/admin/knowledge/search` 可查看候选、重排分数与最终片段；评测模式支持 retrieval-baseline、retrieval、agent、tools。ai 模式下后两种会调用真实模型并产生费用。服务异常会明确降级说明；涉及写操作的结果不确定时，先核实已有工单，不要随意换幂等键重试。

内置示例知识在服务启动时写入或更新，因此直接修改 / 删除这些内置文档，重启后可能被初始化逻辑覆盖 / 恢复。体验自建知识时建议使用新的 documentId。

## 8. 看懂业务后再看代码

按问题定位代码，比逐个类阅读更快。下列路径均相对于项目根目录：

| 你想理解的问题 | 代码入口 |
| --- | --- |
| 页面如何发问、确认、重试？ | src/main/resources/static/app.js |
| 演示设备和知识从哪里来？ | config/DemoDataConfiguration.java、config/KnowledgeSeedConfiguration.java |
| 一句话怎样分配到业务功能？ | agent/DemoAiResponder.java；真实模型看 agent/SpringAiResponder.java |
| 哪些设备能查、耗材如何判断？ | tool/AgentTools.java |
| 工单怎样防止同一请求重复创建？ | tool/TicketService.java、tool/TicketWriter.java、domain/SupportTicket.java |
| 手册怎样被检索、返回来源？ | rag/KnowledgeService.java |

表中的 Java 路径前缀为 `src/main/java/com/example/supportagent/`。进一步阅读 [实现与带读指南](IMPLEMENTATION_GUIDE.md)。

完成上面体验后，试着用自己的话回答：服务谁、解决什么问题、哪些操作只读、哪个操作写入数据、为什么报修要确认、当前工单流程做到哪一步。能说明白这些，就已经掌握项目的主要业务。
