# 面试指南：Java 基础 + RAG + Agent

本文包含通用面试知识，不代表每种组件都已在本项目实现。当前项目的具体实现、测试和局限请对照 [学习路线](LEARNING_PATH.md) 与 [验证记录](VERIFICATION.md)。例如当前重排为 BM25 融合，不是 Cross Encoder；退避未加随机抖动；没有 MQ 或分布式熔断。

不要背概念定义。推荐统一按“结论 -> 原理 -> 项目例子 -> 边界/改进”回答。这样既清楚，也不容易被追问两句就断掉。

## 一分钟项目介绍

> 我做了一个基于 Spring Boot 4 和 Spring AI 2 的智能设备售后 Agent。它支持三类能力：第一类是产品手册 RAG 问答并返回来源；第二类是通过 Function Tool 查询设备、耗材和工单；第三类是经过用户确认后创建售后工单。模型使用 DeepSeek 的 OpenAI-compatible 接口，业务层通过自定义 AiResponder 隔离模型厂商。工程上我重点做了多租户与用户级权限、Redis 会话记忆、PgVector 文档增删改、写工具二次确认、数据库唯一键幂等、超时与工具次数限制、SSE、Prometheus 指标，以及 50 条离线评测集。默认 Profile 有确定性替身，不需要密钥也能做回归测试；真实模型通过 ai Profile 启用。

如果面试官问“你最有价值的工作是什么”，不要回答“接了 DeepSeek API”。可以说：

> 最有价值的是把概率性模型放进确定性的企业边界。比如 tenantId 和确认状态由服务端 ToolContext 注入，工具内部再次按租户和 owner 校验；创建工单由确认门禁、幂等键和数据库唯一约束共同保护。这样即使模型被提示词注入或重复调用，也不能越权或重复写入。

# 第一类：Java 后端系统复习

## 1. Spring Boot 自动配置、AOP、事务失效

### Q1：Spring Boot 自动配置原理是什么？

答：启动类的 `@SpringBootApplication` 包含自动配置能力。Boot 根据 classpath、配置属性、已有 Bean 等条件导入自动配置类，常见条件是 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 和 `@ConditionalOnProperty`。自动配置提供默认值，用户声明自己的 Bean 通常可以覆盖。排查时看条件评估报告，而不是猜。

项目例子：引入 OpenAI Starter 后，即使 chat 设为 none，语音模型自动配置仍默认匹配并要求密钥。最后根据报告找到 `spring.ai.model.audio.speech` 等条件，把没使用的模型类型逐项关闭。

### Q2：Spring AOP 为什么会有自调用失效？

答：声明式事务、缓存和异步通常通过代理实现。外部调用先进入代理，代理再开启事务并调用目标对象；`this.method()` 是目标对象内部直接调用，不经过代理，所以方法上的增强不会触发。private、final 方法或者手动 new 出来的对象也常绕过代理。

项目例子：幂等插入需要 `REQUIRES_NEW`，所以我把它拆到 `TicketWriter` Bean，由 `TicketService` 跨 Bean 调用，避免本类自调用。

### Q3：常见事务失效场景有哪些？

答：自调用；对象不受 Spring 管理；异常被吃掉；默认只对 RuntimeException 回滚而实际抛出 checked exception；方法不是可代理的 public 方法；新线程不继承原线程事务；数据库引擎不支持事务；传播级别理解错误。回答时最好说明：是否回滚取决于异常有没有穿过事务拦截器，而不只是代码里有没有异常。

### Q4：`REQUIRED` 和 `REQUIRES_NEW` 有什么区别？

答：`REQUIRED` 有事务就加入，没有就新建；`REQUIRES_NEW` 会挂起外层事务，自己开启并独立提交/回滚。它适合需要隔离提交结果的短操作，但会额外占数据库连接，嵌套过深可能耗尽连接池。

项目例子：并发插入唯一键失败后，失败事务已经标记回滚，不能继续在同一事务里查赢家，所以插入放进独立新事务，外层捕获冲突再查询。

## 2. MySQL 索引和事务

### Q5：联合索引如何决定能否使用？

答：B+Tree 联合索引按列顺序排序，通常遵循最左前缀。等值条件可以连续利用索引；遇到范围条件后，后面的列通常不能继续用于缩小扫描区间，但可能用于索引下推过滤。是否走索引最终由优化器根据选择性和成本决定，要看 `EXPLAIN`/`EXPLAIN ANALYZE`。

项目映射：工单高频查询可建立 `(tenant_id, owner_id, device_id, status, created_at)`，因为查询先按前四列等值过滤，再按创建时间排序。

### Q6：覆盖索引、回表、索引下推是什么？

答：二级索引叶子节点保存索引列和主键。查询列都在索引中就是覆盖索引，无需根据主键回聚簇索引；缺少列时需要回表。索引下推是存储引擎在遍历索引时先利用可判断的条件过滤，减少回表次数。

### Q7：MVCC 和隔离级别怎么解释？

答：InnoDB 通过 undo log、事务 ID 和 Read View 提供一致性读。读已提交通常每条语句生成新 Read View，可看到其他事务后来提交的数据；可重复读通常在事务第一次一致性读时建立 Read View，后续保持一致。当前读如 `for update` 走锁机制。可重复读结合 next-key lock 处理范围当前读下的幻读问题。

### Q8：为什么幂等最终要靠唯一约束？

答：`select if absent -> insert` 不是原子操作，并发线程可能都查不到。应用锁可能过期、节点故障或覆盖范围不完整；数据库唯一约束在最终写入点裁决，只有一个事务成功。正确做法是业务幂等键 + 唯一索引 + 捕获重复键后读取已有结果。

项目例子：`support_tickets` 对 `(tenant_id,idempotency_key)` 建唯一约束，12 路并发测试最终返回同一 ticketId。

## 3. Redis 缓存一致性

### Q9：Cache Aside 更新数据库和缓存的标准做法是什么？

答：读时先查缓存，未命中读库并回填；写时先更新数据库，提交成功后删除缓存。通常选择删除而不是直接更新，因为更新缓存可能基于旧数据且浪费写入。它仍是最终一致性，极端并发下可能发生旧值回填。

### Q10：怎样降低数据库与缓存不一致？

答：先保证数据库是事实源；删除失败要重试，可以通过事务消息、Outbox、binlog/CDC 驱动失效；热点 key 可使用版本号、较短 TTL 或逻辑过期；对一致性要求极高的读绕过缓存或使用串行化方案。延迟双删只能缩小窗口，不是严格证明。

### Q11：缓存穿透、击穿、雪崩怎么区分？

答：穿透是大量查询不存在数据，可用参数校验、空值缓存、布隆过滤器；击穿是热点 key 过期瞬间大量回源，可用互斥重建、逻辑过期、热点预热；雪崩是大量 key 同时失效或 Redis 故障，可用 TTL 随机化、多级缓存、限流降级和高可用。

项目映射：本项目 Redis 存会话而非 Cache Aside；key 必须含 tenant/user/conversation，设置 TTL 和最大历史条数，解决串会话和无限增长问题。

## 4. MQ 重复消费与幂等

### Q12：为什么 MQ 很难保证业务 exactly-once？

答：Broker 的投递确认和业务数据库提交是两个系统。业务已提交但 ACK 丢失时消息会再次投递，所以常见语义是 at-least-once。Exactly-once 往往只在限定边界内成立，业务消费者仍应幂等。

### Q13：消费者如何做幂等？

答：为事件定义稳定 eventId，在业务库建唯一键或幂等记录；消费时在同一事务里写幂等记录和业务数据。重复键意味着已经处理，直接返回成功。金额扣减等场景还可以用状态机和条件更新，例如 `update ... where status=INIT`。

### Q14：如何解决“本地事务成功但消息没发出去”？

答：使用事务消息，或本地 Outbox：业务数据和待发送事件在同一数据库事务写入，后台任务投递并重试，消费者继续保持幂等。不能用一个普通 try/catch 假装跨数据库和 MQ 原子。

项目映射：知识向量与 manifest 目前也存在跨资源一致性问题，生产可用导入任务表/Outbox 标记 PENDING、INDEXED、FAILED，再做补偿。

## 5. 线程池与 CompletableFuture

### Q15：线程池核心参数怎么讲？

答：核心线程先处理；达到 core 后任务进入队列；队列满才扩到 max；再满触发拒绝策略。无界队列会让 maxPoolSize 基本失效并可能堆积到 OOM。参数应结合任务是 CPU 密集还是 I/O 密集、下游承载能力、连接池大小和目标延迟压测。

### Q16：`CompletableFuture` 常见坑有哪些？

答：不指定 Executor 会用 commonPool，可能与其他任务互相影响；`join` 包装成 CompletionException，要解包根因；多个 future 中一个失败时要定义整体策略；超时不会必然中断已经发出的网络请求，还需要 HTTP 客户端超时；异步线程不会自动继承事务和 ThreadLocal/MDC。

项目例子：同步 Agent 调用放到专用有限线程池，并使用 `orTimeout`；身份不依赖 ThreadLocal，而是显式作为参数传入。

### Q17：为什么不能随便把所有调用都并行？

答：并行只适合互相独立的步骤。Agent 的下一次模型调用依赖上一次 Tool 结果，不能并行；多个只读 Tool 如果模型一次返回多个独立调用可以并行，但写 Tool、顺序状态变更和共享限额必须谨慎。并行度还要服从数据库连接池、模型限流和下游 QPS。

## 6. JVM、GC 与线上排查

### Q18：线上 CPU 飙高怎么排查？

答：先看实例、时间窗口和流量是否变化；用系统工具找到高 CPU 进程和线程，把线程 ID 转为十六进制，在线程栈中定位；结合火焰图/JFR 看热点方法；同时排除频繁 GC、死循环、自旋、正则回溯和日志序列化。最后用监控和变更记录验证根因，而不是只重启。

### Q19：内存持续上涨怎么排查？

答：先区分堆、Metaspace、直接内存和操作系统页缓存；看 GC 后老年代是否能回落。怀疑堆泄漏时保留 heap dump，用 dominator tree、retained size 和 GC roots 找持有链。还要检查线程、连接、Buffer、类加载器。生产 dump 可能很大且含敏感数据，要评估磁盘和权限。

项目例子：会话历史限制条数并在 Redis 设置 TTL，就是避免无界对象增长；线程池队列也设为 100 而不是无界。

### Q20：G1 的核心思路是什么？

答：G1 把堆划分成 Region，按收益优先回收垃圾最多的 Region，目标是可预测停顿。年轻代回收后，老年代达到阈值会启动并发标记，再进行 Mixed GC。排查时关注分配速率、晋升、Humongous 对象、暂停时间和并发标记是否跟得上，不能只背参数。

## 7. 限流、熔断和分布式系统

### Q21：限流、熔断、降级的区别？

答：限流控制进入系统的请求速率，保护容量；熔断根据下游失败率或慢调用主动停止请求，让下游恢复；降级是在资源不足或依赖不可用时返回较低质量但可接受的结果。三者通常配合：先限流，调用失败达到阈值后熔断，最后走缓存、规则回答或人工入口。

### Q22：固定窗口、滑动窗口、漏桶、令牌桶怎么选？

答：固定窗口简单但边界会突发；滑动窗口更平滑但状态更多；漏桶按恒定速率流出，适合严格整形；令牌桶按速率补充 token，允许一定突发，API 网关最常用。分布式限流常用 Redis + Lua 保证判断与扣减原子，但要考虑 Redis 故障时 fail-open 还是 fail-close。

### Q23：重试为什么可能放大故障？

答：超时往往意味着下游已经过载，多个上游立即重试会形成重试风暴。应只重试幂等、瞬时错误，设置次数上限、指数退避和随机抖动，并纳入总超时预算；写操作必须有幂等键。熔断器和隔离舱用于限制故障扩散。

### Q24：分布式一致性如何回答？

答：先明确一致性要求和失败模型。单库优先本地事务；跨服务常用最终一致性、Outbox、事务消息、Saga/补偿；读多写少可以接受缓存最终一致。不要一上来就说 2PC。关键是状态可追踪、操作幂等、失败可重试、超时可补偿、人工可介入。

项目映射：Agent 的外部模型不可纳入数据库事务，所以先让模型提出动作，Java 校验后做短事务；不把长时间模型调用包在数据库事务里。

# 第二类：Spring AI、RAG 与 Agent 面试题

## 1. 概念与调用链

### Q25：Prompt、RAG、Function Tool、Agent 分别是什么关系？

答：Prompt 给模型任务、上下文和行为规则；RAG 在回答前从外部知识库检索证据，解决私有知识和知识时效问题；Function Tool 把可执行的业务能力以结构化 schema 提供给模型；Agent 是在目标驱动下反复选择 Tool、观察结果、继续推理直到完成任务的控制循环。RAG 本身也可以封装成一个检索 Tool。

### Q26：Spring AI 帮你做了什么，没帮你做什么？

答：它统一了 ChatModel/EmbeddingModel/VectorStore 抽象、Prompt 与消息、Tool schema 和调用循环、Advisor、可观测接口，减少厂商 SDK 差异。它不会替我完成业务权限、数据一致性、幂等、评测集设计、异常降级和成本治理，这些仍是应用工程责任。

### Q27：一次 Tool Calling 的完整流程是什么？

答：应用把历史消息、用户问题和工具 schema 发给模型；模型返回工具名和 JSON 参数；Spring AI 根据名称定位 Java Tool；框架传递模型参数和服务端 ToolContext；工具做权限校验并执行业务；结果作为 tool message 加回上下文；模型结合结果生成最终回答。如果仍返回工具调用，循环继续，直到普通回答或触发次数/超时限制。

### Q28：为什么要自己定义 `AiResponder`，直接注入 ChatClient 不行吗？

答：小 Demo 可以直接用。项目引入端口是为了让业务编排不绑定模型和网络：无密钥测试使用确定性实现，真实环境使用 Spring AI；以后也能增加模型路由、降级模型或回放实现。代价是多一层抽象，所以只有需要可测试性和可替换性时才值得。

## 2. Prompt 工程

### Q29：如何设计一个可靠的系统 Prompt？

答：写清角色和目标、可用数据边界、何时必须调用哪个工具、无依据时如何处理、输出格式和禁止行为；用少量正反例消除歧义。Prompt 要版本化，并用固定评测集比较，而不是靠主观感觉反复改字。

### Q30：如何防 Prompt Injection？

答：先承认无法只靠 Prompt 完全防住。把外部文档视为不可信数据，用清晰分隔和指令层级；敏感 Tool 最小化暴露；身份和权限从服务端注入；工具内部二次鉴权；输出做校验；高风险写操作人工确认；记录调用审计。即使模型服从恶意文档，确定性代码也不能允许越权。

### Q31：Temperature 越低就不会幻觉吗？

答：不是。低 Temperature 主要降低采样随机性，让输出更稳定，不保证事实正确。降低幻觉要靠检索证据、强制引用、没有证据拒答、工具获取实时事实、结构化输出校验和评测。项目把温度设为 0.1 是为稳定，不把它当安全保证。

## 3. RAG 细节

### Q32：为什么需要 RAG，微调不行吗？

答：RAG 适合频繁变化、需要引用、带权限的企业知识，更新文档即可生效；微调更适合改变模型行为、风格或特定任务能力，不适合精确存储大量变化事实。两者可以结合，但本项目的手册与租户知识优先 RAG。

### Q33：RAG 的 chunk 大小怎么定？

答：取决于文档结构、Embedding 模型、问题粒度和生成上下文预算。太小会丢上下文，太大容易混入无关内容并减少召回粒度。一般先按标题/段落/句子语义切，再设最大长度和 overlap，通过 Recall@K、引用准确率和成本实验选择，而不是相信一个固定数字。

### Q34：向量检索中的 topK 和 threshold 如何取舍？

答：topK 太小会漏证据，太大会引入噪声和 Token 成本；threshold 太高容易拒答，太低容易拿无关内容生成幻觉。先扩大初召回，再用关键词/重排模型排序，最后把少量高质量片段交给模型。参数必须按真实数据集调优，并观察“召回失败”和“生成未利用证据”是不同问题。

### Q35：Hybrid Search 和 Rerank 为什么有用？

答：向量擅长语义相似，但产品型号、错误码、订单号等精确词可能更适合 BM25；混合检索合并两种候选，再由 Cross-Encoder/Reranker 对 query-document 对打分，可提升 top 几条精度。代价是额外延迟和模型成本，可对候选数做限制和缓存。

### Q36：如何做多租户 RAG 隔离？

答：文档入库 metadata 写 tenantId，查询时由服务端身份生成过滤条件，而不是接受模型或用户自由拼接的 tenantId。向量数据库也应按租户做行级策略、分区、collection 或独立库，取决于隔离级别。测试放入另一个租户的诱饵密文，专门断言当前租户永远检索不到。

### Q37：知识库文档更新和删除怎么做？

答：为源文档和 chunk 设计稳定 ID。更新时找到旧 chunk IDs、删除旧向量、重新切片嵌入并写入，再更新版本清单；删除同理。本项目用 `KnowledgeManifest` 持久化 chunk 清单。更高可靠性要用导入任务状态机和补偿，因为向量库和业务表不一定支持同一事务。

### Q38：如何评估 RAG？

答：拆成检索和生成。检索看 Recall@K、MRR、NDCG；生成看正确性、忠实度、引用匹配、拒答是否合理。还看端到端延迟、Token 和成本。先有人工标注的小型黄金集，CI 做稳定回归，大规模评测可使用 LLM-as-judge，但需要人工抽检和校准偏差。

## 4. Tool 与 Agent 可靠性

### Q39：Tool 的设计原则是什么？

答：单一职责、名称明确、参数 schema 尽量小、返回结构稳定、错误可识别；读写副作用要区分；执行应有超时、权限、限额、审计和幂等。不要把一个万能 SQL/HTTP Tool 直接开放给模型，这会扩大攻击面和不可控性。

### Q40：模型生成了非法参数怎么办？

答：schema/Bean Validation 做格式校验，工具内部做业务校验和资源归属校验；错误返回稳定 code，让模型可以修正或向用户解释。不能因为参数来自模型就跳过校验。对于金额、收货地址、删除等高风险字段，要把最终值展示给用户确认。

### Q41：为什么写 Tool 要二次确认？

答：用户的一句话可能有歧义，模型也可能误判或被注入。先生成“准备执行的动作和参数”，用户确认后服务端在当前请求设置 `confirmedWrite`；Tool 只相信这个可信上下文。确认还应有短期 action token，绑定用户、动作、参数摘要和过期时间，防止确认被重放到另一动作。

### Q42：Agent 为什么会死循环，怎么处理？

答：工具描述重叠、工具结果不明确、模型无法满足目标时可能重复调用。设置每工具和总调用次数；设置整次请求的 deadline；记录每轮 tool name/arguments/result；重复相同调用时短路；必要时由状态机明确下一步。项目配置单工具与总次数最大 8，并设置 30 秒总超时。

### Q43：什么时候用简单 Tool Calling，什么时候用 LangGraph/工作流？

答：单轮或少量工具、步骤由模型动态决定、失败可以整次重试时，ChatClient Tool Calling 足够。若流程有明确多阶段状态、长时间运行、暂停恢复、人工审批、并行分支、补偿和持久化 checkpoint，就适合图/状态机。框架层级应由业务复杂度驱动。

### Q44：Agent 的 Memory 存什么，不存什么？

答：短期存完成当前对话所需的用户/助手消息；Tool 中间历史通常由一次调用循环管理。长期只保存经过选择的用户偏好、摘要或业务状态，并提供 TTL、删除、脱敏和权限。密码、密钥、完整敏感文档和无界原始历史不应直接塞入 Memory。

### Q45：模型服务超时或限流怎么办？

答：HTTP 连接、读取和整次 Agent 都要有超时；对 429/可恢复网络错误做有限指数退避和抖动，但遵守总 deadline；用 bulkhead 限制并发；熔断后降级到检索原文、规则回答或人工客服。写操作重试必须携带同一幂等键，不能重新生成。

### Q46：流式输出有哪些坑？

答：SSE 连接会长期占用资源，要限制时长和并发；客户端断开要取消上游订阅；中途失败时已显示的部分文本不能当完整答案；工具调用阶段可能暂时没有 token；代理层要关闭缓冲；会话历史只应在流成功结束后写入完整答案。生产还应发送结构化 error/done 事件。

## 5. 项目深挖题

### Q47：你的 RAG 为什么不用 DeepSeek Embedding？

答：DeepSeek 承担对话推理，Embedding 是独立 Bean。默认是无密钥回归的 Hashing 替身；semantic Profile 使用真实的本地 multilingual MiniLM ONNX 模型。Chat 模型和 Embedding 可以不同，但同一索引入库与查询必须使用相同向量模型。切换 semantic 时使用独立向量表与清单命名空间。

### Q48：真实 AI 模式怎样保证 citations 不是模型编造的？

答：`search_product_knowledge` 执行时用服务端 traceId 把真实 RetrievedChunk 记录到 `ToolTraceStore`；同步回答结束后由 `SpringAiResponder` 取出，SSE 则在 done 事件取出。title/source/score 都来自 VectorStore metadata，不解析模型正文。异常路径也会 drain，避免内存残留。单机内存实现适合一次请求；跨节点异步工作流应改成带 TTL 的 Redis 或链路追踪存储。

### Q49：为什么 API Key 和请求 Header 方案不算生产鉴权？

答：它是为了突出 Agent 安全边界的最小演示。生产应由网关/JWT/OAuth2 建立可信 Principal，tenant 和 user 从经过签名的 claim 或服务端会话获得，不能允许客户端任意填写 Header；服务间还需 mTLS、密钥轮换和审计。

### Q50：这个项目下一步你会怎么演进？

答：当前已有本地真实 Embedding、BM25 重排、引用轨迹、重试与进程内熔断。下一步可补独立词法候选召回、Testcontainers、网关限流、Flyway、OpenTelemetry、知识导入补偿和基于真实日志的人工标注评测。每项都应用具体指标验证，不应只增加组件。

# 反问与答题纪律

如果面试官说“这不就是调 API 吗”，可以回答：

> 模型调用确实不难，难点是把不确定输出接到确定业务上。我能具体说明 Tool 的权限来源、RAG 租户过滤、写操作幂等、事务边界、超时限额和效果回归；这些部分仍然是典型 Java 后端工程，只是上游决策组件换成了大模型。

不要声称：

- “RAG 能彻底消除幻觉。”
- “加了 Prompt 就绝对不会越权。”
- “Redis 分布式锁保证 exactly-once。”
- “本地 50 条用例通过就达到生产准确率。”
- “我实现了多 Agent”，除非你真的加入了多个独立角色、状态和协作机制。

可以主动反问：贵司 Agent 目前主要难点在效果、数据治理还是业务系统集成？线上是否有固定评测集和写工具审批机制？这会把交流拉回你最有优势的 Java 工程落地部分。
